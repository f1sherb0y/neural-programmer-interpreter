# Neural Programmer-Interpreter: Addition Reproduction

This repository contains a modern PyTorch reproduction of the addition experiments from Reed and de Freitas, [Neural Programmer-Interpreters](https://arxiv.org/abs/1511.06279).

The original third-party TensorFlow 0.x implementation remains under `model/` and `tasks/` for reference. The supported implementation is under `modern_npi/` and uses Python 3.12, PyTorch 2.13, recursive program calls, and dynamic scratchpads.

## Reproduced Results

The checked-in model was trained from seed 1 on 32 addition traces at each input length from 1 through 20, matching the sample count stated in Appendix 6.3 of the paper.

| Test length | Correct | Sequence accuracy |
|---:|---:|---:|
| 1 | 32 / 32 | 100% |
| 5 | 32 / 32 | 100% |
| 10 | 1,000 / 1,000 | 100% |
| 20 | 32 / 32 | 100% |
| 50 | 32 / 32 | 100% |
| 100 | 32 / 32 | 100% |
| 500 | 2 / 2 | 100% |
| 1,000 | 2 / 2 | 100% |
| 3,000 | 2 / 2 | 100% |

These are whole-execution results. Every program selection, argument, return decision, and environment action is generated by the model in closed loop. The long-length sample count is deliberately reported; two successful examples are evidence of extrapolation, not a high-confidence estimate of 3,000-digit accuracy.

## Architecture

See the [Mermaid architecture and recursive-state diagram](docs/npi_addition_architecture.md).

The model implements the paper's three learned outputs:

- return/end logits;
- a key matched against learned program keys;
- three program-argument logits.

A single two-layer, 256-unit LSTM core is conditioned by learned embeddings for five programs:

```text
ADD -> ADD1, LSHIFT
ADD1 -> ACT, CARRY
CARRY -> ACT
LSHIFT -> ACT
ACT -> environment transition, then return
```

Each invocation receives a fresh recurrent state. A caller retains its own state while a child runs, then resumes after the child returns. `ACT` is an actual program invocation; its arguments select pointer movement or scratchpad writing.

## Paper Qualification

The authors did not publish the experiment source, and the paper does not specify how addition observes that a pointer is at the most-significant input column. A local boundary signal is necessary for length-independent termination. This reproduction adds one explicit `at_most_significant_input` bit to the four observed scratchpad digits. The result therefore reproduces the claimed behavior and training-length split, but it is not an exact reconstruction of an unreleased implementation.

Other disclosed differences:

- PyTorch 2.13 replaces the paper's historical framework.
- Adam uses a `3e-4` learning rate instead of the paper's `1e-4`.
- Episodes are batched by invocation length instead of using the paper's adaptive curriculum.
- Program, key, and state embedding dimensions are implementation choices because the paper does not fully specify them.

## Setup

The exact Python dependency graph is recorded in `uv.lock`:

```bash
uv sync --frozen
```

A Conda-compatible environment is also provided:

```bash
conda env create -f environment.yml
conda activate neural-programmer-interpreter
```

Python 3.12 is required. The locked PyTorch build uses CUDA when an NVIDIA GPU and compatible driver are available; ordinary training and evaluation commands also support `--device cpu`.

## Reproduce

Train on 32 examples per length from 1 through 20, then evaluate:

```bash
uv run python main.py reproduce \
  --epochs 60 \
  --batch-size 256 \
  --lengths 1,5,10,20,50,100,500,1000,3000 \
  --evaluation-examples 32
```

Long lengths use two examples per length to keep the default run bounded. Evaluate 1,000 held-out 10-digit additions with:

```bash
uv run python main.py evaluate \
  --checkpoint artifacts/addition.pt \
  --lengths 10 \
  --evaluation-examples 1000 \
  --results artifacts/addition_10_digit_results.json
```

### Multi-GPU Generalization Sweep

The HPC sweep measures maximum verified graph size against optimizer step, with one curve per maximum training size. A graph size passes only when all 100 deterministic-randomized closed-loop problems have exact NetworkX distances and valid shortest-path parent trees. Candidate sizes are checked in ascending order and evaluation stops at the first failure, so the reported value is a conservative contiguous bound rather than an isolated success at a larger size.

```bash
uv run python -m modern_npi.graph.generalization_sweep \
  --gpu-count 8 \
  --maximum-train-nodes 5,10,15,20 \
  --seeds 1,2 \
  --checkpoint-steps 1000,2000,4000,6000,8000,10000,12000 \
  --generalization-nodes 10,20,30,40,50,75,100,125,150,200 \
  --execution-batch-size 100 \
  --output artifacts/graph_generalization_sweep
```

`--gpu-count` is the number of concurrent GPU workers. Each `(maximum training nodes, seed)` run is assigned to one GPU, so keep at least that many run combinations to occupy every requested GPU. Within a worker, up to 100 recursive graph interpreters are advanced in one dynamic GPU batch. Runs are resumable at sampled optimizer steps.

The sweep writes compact checkpoints, per-step evaluation JSON, `sweep_results.json`, `sweep_results.csv`, and:

```text
artifacts/graph_generalization_sweep/generalization_vs_steps.png
artifacts/graph_generalization_sweep/generalization_vs_steps.pdf
```
